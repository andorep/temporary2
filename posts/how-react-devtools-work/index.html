Great now that I have a goal, I need to figure out how React DevTools work under the hood. The first thing I noticed is that React DevTools Standolone is inside the same repo as React itself, under the packages/react-devtools folder.

By doing a quick look I saw that this package is basically a creating and spawing an electron application. So where's the actual React DevTools code?

Turns out, the react devtools is split into multiple packages 😵‍💫

So why they decided to split it into multiple packages? My guess is that by doing this they can follow the single responsibility principle, and also they can reuse the code for different approaches.

So how's the React DevTools architecture looks like then? Well, all code related to the devtools is undert the prefix name packages/react-devtools-*, here's summary of the packages that I found:

PackageDescription
react-devtools-coreThis package is collection of low level APIs to support renderers custom renderers.

Now that you know the context, let's dive into more on this rabbit hole.

So the first thing I did was to try to understand how does react devtools know about the React tree of your app. For this I look into the react-devtools-core package, and if you go to the backend.js file, you'll see that there's a function called connectToDevTools

If you explore a little this function, you'll find 3 main concepts in action here:

  • The Bridge
  • The Agent
  • The Store

This 3 concepts are the core for the communication between the React app and the React DevTools. And they are located in the react-devtools-shared

They way they work is the following

  1. The Agent will receive information all events that happen in the React app, and will send this information to the Bridge.
  2. The Bridge is in charge to communicate this information to the store and any other listeners that are interested in this information.
  3. Then Store will now store all of this information, in a way that the React DevTools UI can consume it.
  4. Another important thing is that the Bridge also notify the React DevTools UI about the events, but to simplify things, we will not explore this part.

But now you get the idea, right? Something will communicate to the Agent about the React tree, and then every thing else will go from there.

Now, what's this something that will communicate to the Agent about the React tree?

Well this actually the window.__REACT_DEVTOOLS_GLOBAL_HOOK__ variable, which you can suscribe to be notified about changes in the React tree (Not quite, but we will get to that later).

Note:

window.__REACT_DEVTOOLS_GLOBAL_HOOK__ does notify the agent about other things too, but we will not explore that here.

How does this hook work? Well, if you check the from the initBackend:39~58 , you'll see that this function is suscribes the Agent to the hook events.

The one event we are interested in is the hook.sub('operations', agent.onHookOperations), which will notify the agent about the changes in the React tree.

After this, the agent will start receiving information about the React tree, and will send this information to the Bridge, and then to the Store.

The last piece we are missing so far is the UI devtools, which is call DevTools.js and you can find it in the react-devtools-shared package too.

Great! Now we have a better picture of how things work. But we aren't done yet...

If you noticed, I said that we can subscribe to the hook.sub('operations', agent.onHookOperations) event to be notified about changes in the React tree, but aren't you curious why isn't it called something like hook.sub('reactTreeChange', agent.onHookOperations)?

Well this is because the we aren't getting the whole React tree, everytime something changes in your React app, this will be very inefficient, don't you think?

That's why what we get instead is a list of operations that tell you what's happening in the app. So the diagram is still incomplete. To have a better understanding of this, we will need to explore what are these operations.

(I guess this have to do something with React Fiber, and how the diff algorithm works, but I will not go into that, I'm not an expert in that area yet).

Operations... Great another term....

Operations are basically a list of instructions that tell you what happened in the React tree. For example, if you add a new component to your app, you will get an operation that tells you that a new component was added.

This operations are represented as an array of numbers, instead of objects or strings, to make it more serializable and efficient to send over the bridge.

So we know that are numbers and we recieve an list of them, but how do we know what each number means? The list of are constants that you can find in the constants.js file.

Basically when you recieve a 1 it means that a new component was added, when you recieve a 2 it means that a component was removed, and so on.

But things are not that simple, because each operations is tight to certain number of arguments, for example, [1,4,2] if we take a look at this array of operations, the first number is 1, which means that a new component was added, but what about the 4 and the 2?

You may be thinking that these will be another operations right? TREE_OPERATION_UPDATE_TREE_BASE_DURATION and TREE_OPERATION_REMOVE respectively, but no, these are the arguments for the first operation.

They way it works is that each operation has a fixed number of arguments, that indicate more information about the operation. For example, in this scenario, the 4 is the id of the component that was added, and the 2 is the type of the component.

So if you want to understand what each operation means, you will need to look at the onBridgeOperations function in the agent.js file, where you will see a big switch statement that tells you what will every operation do.

At this point you may be totally lost, and that's okay, I was too, probably even more than you are right now.

But no worry, because I have more confusing stuff for you.

Besides the operations, I just explain, the first elements of the array are some metadata about the operations, that this process need to work properly.

The first two elements are the rendererID and the rootID.

The next element is the number of operations that represent the all the names of the components, so if you if the number is 43, then the next 43 elements will be use to build the string names of the components.

After this, the next element is the number of operations that represent the number of strings required to build the first component name, so if the number is 4, then the next 4 elements will be use to build the string name of the first component and so on.

I call all this init operations. Is not the actual name but is easier to remember for me.

    Soo... are we finally done? Well... unfortunately not yet...

    You already know that the operations are just a list of numbers, with the things that happened in the React tree. You also know that the Agent will receive this operations and will send them to the Bridge, and then to the Store will process them and store them in a way that the Devtools.js can consume them.

    So you are probably thinking if that's not all, what else is there that we don't know already?

    The question resides in the window.__REACT_DEVTOOLS_GLOBAL_HOOK__ variable again. This were all the process start, but out of the box, this variable will not contain the necessary logic to notify the Agent about the operations.

    This is because the React Devtools calls another process where it injects the necessary logic to make this possible.

    We can find a function called installHook in the hook.js file, that will inject all the logic.

    Because remember you WILL NOT GET THE WHOLE REACT TREE you will only get the operations that tell you what happened in the React tree. So if you miss some of these operations, the store will not be able to reecreate whole React tree in the propert order.
